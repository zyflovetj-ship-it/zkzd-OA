# zk-oa 代码与功能齐全度评估报告

- 评估日期：2026-09-28
- 评估范围：`zk-oa/`（FastAPI + PostgreSQL/SQLite 后端、React 19 + AntD 5 前端）
- 评估方式：静态核对（路由/接口/权限/菜单一致性）+ **真实启动后端跑 HTTP 冒烟** + 单元/集成测试 + 前端类型检查
- 结论先行：**修复前该系统无法启动、无法迁移、写接口全部 500，属于"代码齐全但从未真正跑通"；修复 11 处缺陷后，后端 48 项测试全绿、83 项 HTTP 冒烟全通过、前端类型检查 0 错误。功能覆盖 OA 核心审批闭环，但考勤/报销/公文等模块缺失，委托审批是半成品，生产构建仍需在标准环境验证。**

## 二、发现并已修复的缺陷（11 处改动）

> 下列 1–6 为**启动级阻塞**：任意一条存在，系统都完全跑不起来；7–9 为**核心接口必现 500**；10–11 为正确性/可维护性问题。

### 1. 路由前缀重复，前端所有请求 404 【致命】
- 位置：`backend/app/api/routers.py`
- 症状：容器路由 `api = APIRouter(prefix="/api")` 与各子路由自带的 `/api/...` 前缀叠加，实际挂载成 `/api/api/auth/login`、`/api/api/users`……而前端按 `/api/**` 请求，**全部 404**。
- 修复：容器路由改为 `APIRouter()`（并加注释说明不可再加前缀）。

### 2. `from sqlalchemy import coalesce` 不存在 【致命】
- 位置：`backend/app/repositories.py:4`
- 症状：SQLAlchemy 2.0.36 没有顶层 `coalesce` 导出（已用官方 wheel 比对确认），应用 **import 即失败**；代码里实际只用 `func.coalesce`。
- 修复：移除该导入。

### 3. 类体内 `def list` 遮蔽内置 `list`，注解求值崩溃 【致命】
- 位置：`backend/app/repositories.py`、`backend/app/services.py`
- 症状：类里先定义了 `async def list(...)`，其后的 `-> list[dict]` 在**类定义期**解析到该函数 → `TypeError: 'function' object is not subscriptable`，import 失败（`compileall` 只查语法，查不出）。
- 修复：两文件加 `from __future__ import annotations`（注解改为惰性字符串）。

### 4. Department↔User 双外键未指定 `foreign_keys` 【致命】
- 位置：`backend/app/models.py`（`Department.members` / `User.department`）
- 症状：`users.department_id` 与 `departments.manager_id` 构成两条外键路径，SQLAlchemy 配置映射时报 `Could not determine join condition ... multiple foreign key paths`，**任何涉及用户/部门的查询都会失败**。
- 修复：两处 relationship 显式声明 `foreign_keys`。

### 5. 关键字式日志调用导致服务无法启动 【致命】
- 位置：`backend/app/main.py:40`（及 `:59`、`middleware.py`、`scheduler.py`、`services.py` 共 7 处调用点）
- 症状：`logger.info("startup", env=...)` 使用 structlog 风格关键字参数，但 `get_logger()` 返回的是标准库 `logging.Logger` → `TypeError: _log() got an unexpected keyword argument 'env'` → **lifespan 失败，服务直接退出**。
- 修复：新增 `StructLogger`，把额外关键字并入 LogRecord，由 `JsonFormatter` 输出为 JSON 字段（保持原设计意图）。

### 6. Alembic 0001 在 SQLite 上无法执行 【致命】
- 位置：`backend/migrations/versions/0001_initial.py`
- 症状：用 `op.create_foreign_key` 补循环外键，SQLite 不支持 ALTER 约束 → `NotImplementedError`，而 `run.sh` / DEPLOYMENT.md 的"PC 本地 SQLite 部署"第一步就失败。
- 修复：SQLite 走 `batch_alter_table`，其他方言保持原逻辑；已加回归测试。

### 7. 异步会话惰性加载 → 多个核心接口 500 【致命】
- 症状：`MissingGreenlet: greenlet_spawn has not been called`，响应序列化时触发惰性 IO。
- 涉及接口（均实测复现）：
  - `POST /api/workflows/instances`（发起流程）—— `WorkflowInstanceOut.tasks` 未加载；
  - `decide / transfer / addsign / withdraw`（审批动作）—— 6 处 `session.refresh(instance)` 只刷新标量、不加载集合；
  - `POST /api/users`（新建账户）—— `_with_role_name` 读 `user.role.name`；
  - `PATCH /api/users/{id}`（编辑账户）—— 更新后 role 未加载/可能过期。
- 修复：
  - `WorkflowService._refresh_with_tasks()`：`refresh(instance, ["tasks"])`，替换 6 处；
  - `WorkflowRepository.get_task()` 增加 `instance → tasks` 嵌套 `selectinload`；`create_instance()` 落库后按 eager 重新取回；
  - `UserRepository.get_with_relations()`（`populate_existing` + `selectinload(role/department)`），新建/更新用户后统一取回。

### 8. `UserUpdate` 缺 `username` 字段 【高】
- 位置：`backend/app/schemas.py`
- 症状：服务层 `UserService.update` 无条件读 `data.username` → `AttributeError` → **编辑用户 100% 500**（修复 7 之后立刻暴露的下一个问题）。
- 修复：`UserUpdate` 补 `username` 字段（带长度校验，默认 None 表示不改名）。

### 9. 刷新令牌：唯一性冲突 + naive/aware 时间比较 【高】
- 位置：`backend/app/core/security.py`、`backend/app/services.py`
- 症状 A：刷新令牌是 JWT，`iat/exp` 只有**秒级精度**且无随机串 → 同一秒签发的令牌完全相同，撞 `refresh_tokens.token_hash` 唯一索引 → **同秒登录/刷新随机 500**（`IntegrityError`）。
- 症状 B：`record.expires_at`（库里读出是 naive UTC）与 aware 的 `datetime.now(timezone.utc)` 比较 → `TypeError` → **`POST /api/auth/refresh` 必现 500**；访问令牌 15 分钟过期后前端自动续期失败，用户被迫重新登录。
- 修复：签发加 `jti=uuid4`；新增 `_as_utc()` 统一时间口径。

### 10. aware 时间直接绑定到 naive 列 【中】
- 位置：委托时间窗、建模"今日新增"统计、审计清理切点
- 症状：DB 列为 `DateTime`（无时区，存的是 naive UTC），查询参数却是 aware。SQLite 下退化为字符串比较"侥幸可用"，**PostgreSQL 生产环境会类型冲突**。
- 修复：统一 `.replace(tzinfo=None)`（与写入口径一致）。

### 11. 测试断言与实现不一致 【中】
- 位置：`backend/tests/test_workflow_service.py::test_get_stats_structure`
- 症状：断言 `instances_stat`/`tasks_stat`，而实现与 `WorkflowStatsOut`、前端 `WorkflowMonitor` 一致的是 `instances`/`tasks` → **即使在标准环境 pytest 也必然红**，与 DELIVERY.md「应全绿」的声明不符。
- 修复：断言对齐真实字段。

### 新增测试
- `backend/tests/test_regressions.py`（**10 项**，每项锁定一个上述缺陷）：路由前缀、刷新令牌同秒唯一、登录→刷新→吊销轮换、`UserUpdate.username`、新建/更新用户 role 可加载、发起流程 tasks 已加载、`get_task` 连带加载、Department↔User 关系可配置、**SQLite 迁移可执行**。
- `backend/tests/smoke_live.py`：起服务后可重复执行的 83 项 HTTP 冒烟脚本（含 RBAC 401/403 边界）。

### 3.3 上线前仍需处理（文档中已自述、本次未改）

1. **生产前端构建未验证**：本机 `npm run build` 因 rollup 原生模块 dlopen 被平台拒绝（`ERR_DLOPEN_FAILED`），须在 CI / 标准 Linux/Docker 跑一次（`.github/workflows/ci.yml` 已配好，push 即可验）。
2. 刷新令牌仍存内存 —— 刷新页面即掉线；建议改 `httpOnly + Secure + SameSite` Cookie。
3. 限流 `RATE_LIMIT_PER_MINUTE=0`（关闭）、HTTPS 终止、Nginx `proxy_buffering off`（否则 SSE 不实时）、PostgreSQL 连接池调参。
4. 时区口径：审计时间窗由前端传**本地时间字符串**，库里存 UTC，过滤边界会有 8 小时偏差（不影响正确性，只影响筛选范围）。

## 四、工程质量评价

**优点**
- 分层清晰：router（RBAC 依赖）→ service（事务/业务）→ repository（`selectinload` 防 N+1），错误统一、结构化 JSON 日志带 request_id、审计中间件、优雅停机、SSE 实时推送，配置集中且生产环境快速失败。
- 文档极其详尽（README / DEPLOYMENT / DELIVERY / HARDENING / 各引擎设计文档），部署与迁移步骤可执行。
- 前后端契约一致性很好：55 个前端接口路径、25 个菜单、51 个权限码全部对得上，前端零硬编码 URL。

**主要短板**
- **"静态校验通过"被当成了"可运行"**：`compileall` 查不出 import/注解/映射错误，`tsc` 查不出运行时问题；DELIVERY.md 多处写"标准环境 pytest 应全绿"，但**在标准环境也跑不起来**——致命缺陷全部绕过了既有校验。
- **测试盲区**是系统性的：48 项测试全部只调服务层，不经过**路由注册、响应序列化、中间件、lifespan**，所以 9 处致命/高危 bug 无一被拦住。缺 HTTP 层测试与启动冒烟。
- 未跑过的路径与自述文档有偏差（例如 README 签单接口写 `POST /api/signatures/{ref_type}/{ref_id}`，实际只有 GET 带 ref，POST 在根路径）。

**建议的下一步（按收益排序）**
1. 把 `pytest` + 起服务跑 `tests/smoke_live.py` 加进 CI（约 1 分钟），从此"能不能跑"有硬闸门。
2. 在 CI 里确认 `npm run build` 通过，产出生产镜像。
3. 补齐考勤（打卡/假期余额）与委托审批的管理入口——这是当前最明显的业务缺口。
4. 给 `AuthService` / 路由层补 HTTP 测试（登录、刷新、401/403、响应模型序列化）。
5. 更新 DELIVERY.md 的"验证状态"，把"沙箱未验证"改为真实口径，并记录本次 11 处修复。
