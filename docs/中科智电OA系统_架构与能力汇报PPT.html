PART 01 · 行业演进

OA 的四代演进：从"无纸化"到"智能协同"

理解主流 OA 的架构与能力，先看行业二十年的演进主线——每一代都以一个"引擎"的成熟为标志，最终积累为今天通用的分层架构模式。

GEN 1 · 1998—2005

文档电子化

以收发文、公告、通讯录为核心，替代纸质公文。

  • 公文流转 / 电子公告
  • 通讯录与组织架构
  • 文件共享（FTP / 共享盘）
关键词：无纸化
GEN 2 · 2005—2013

流程电子化

工作流引擎出现，审批从线下签字转为线上流转。

  • 可视化流程设计器
  • 表单 + 流程绑定
  • 会签 / 加签 / 转办等动作
关键词：BPM / 工作流
GEN 3 · 2013—2020

门户与移动化

统一待办门户 + 移动端，消息实时触达，集成 SSO。

  • 待办 / 已办 / 我发起聚合
  • 企微 / 钉钉 / 飞书集成
  • 消息中心与提醒（IM / 短信）
关键词：门户 + 移动办公
GEN 4 · 2020— 至今

低代码与智能化

建模引擎零代码造表，数据看板驱动决策，AI 辅助审批。

  • 低代码实体建模 / 表单引擎
  • BI 看板与预算管控
  • 智能提醒、异常识别、AI 审批
关键词：低代码 + 数据驱动
◆
共性结论 1所有主流 OA 最终都收敛到「门户 + 流程 + 表单 + 数据」四件套，差别在于引擎的成熟度与开放度。
◆
共性结论 2工作流引擎是 OA 的心脏：能否不写代码配置新流程，决定系统能否长期自我演进。
◆
共性结论 3权限与审计是底线能力：RBAC + 数据范围 + 全量操作留痕，缺一不可。
◆
共性结论 4第五代的竞争点已转向数据资产化——流程数据能否直接变成管理看板与预算管控。

PART 04 · 引擎详解

工作流引擎：7 种节点 · 7 项高级动作

引擎核心是纯函数（workflow_engine.py，216 行，零数据库依赖，可独立单测）。图结构、条件路由、并行汇聚、会签策略全部在此完成，服务层只负责持久化与副作用。

01 · 自动

start 发起

入口节点，不产生待办，就地展开。

02 · 人工

approval 审批

单人处理：同意 / 驳回 / 转办。

03 · 人工

countersign 会签

多人并行，策略 all / any / ratio。

04 · 自动

condition 条件

and/or 规则组，可 parallel 全分支命中。

05 · 自动

join 汇聚

只等待被激活分支，互斥分支不死锁。

06 · 自动

notify 抄送

通知指定人，不阻塞主流程。

07 · 终态

end 结束

终态判定并回写业务表。

验证边界 · 必须如实汇报

本仓库当前处于开发沙箱（openharmony / aarch64），该平台存在原生库限制： rollup 原生库无法 dlopen、pydantic 需 Rust 工具链、greenlet（SQLAlchemy 依赖）需 gcc。

  • 已验证：后端 compileall 与 pytest 59 通过；前端 tsc --noEmit 0 错误。
  • 待在标准环境执行：生产构建 npm run build、数据库运行时自检、Docker Compose 部署验证。
已知风险 · 需在下个迭代处理
R1
vite-plugin-pwa 依赖未声明 frontend/vite.config.ts import 了该包，但 package.json / lock / node_modules 均不存在 → npm run dev 与 build 会在加载配置时失败。修复：移除该 import 或显式安装依赖。
R2
重复路由定义 GET /api/expenses/export 在两处定义，后者为死代码，可能导致行为歧义 —— 应去重。
R3
中间件顺序注释与实现不符 限流中间件注释自称"最外层"，但 Starlette 实际顺序为最后 add 者最外层 —— 需订正注释或调整注册顺序。
